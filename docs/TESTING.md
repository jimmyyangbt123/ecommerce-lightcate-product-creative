# 测试与验收

## 三种证据必须分开

1. **自动检查**：仓库结构、引用和件数声明文本。
2. **Agent文字试跑**：看是否执行正确问话、分支和交付形状。
3. **真实图像验收**：实际调用宿主生成后，核商品、文字、场景和排版。

前两项通过不代表第三项通过；更不代表平台准入或转化提升。这里没有伪造的大样本成功率。

## 自动检查

仓库根目录：

```bash
python3 -m unittest discover -s tests -v
python3 tools/validate_repo.py
python3 skills/ecommerce-product-creative/scripts/check_delivery.py examples/delivery.json
```

测试使用Python标准库，覆盖单件/多件标签、乱序归一、最低规格遗漏、标题末尾数量、主图文案不匹配、串入别的链接选项、重复ID、非法计数和命令行退出状态。

`check_delivery.py`读取声明：`listings[].id/pack_counts/title/cover_header`。它不读取图片文件。pack_counts必须来自实际确认数据，不是由检查器核实供应商信息。PASS只代表这些声明之间的格式一致。

`validate_repo.py`检查所需文件、本地Markdown链接、代码块闭合、公开文档中的工作区标记和Skill入口基本结构；不验证正式类目树时效、Markdown渲染像素、Mermaid布局或模型行为。

CI重复上述离线检查；实际远程运行状态以作者上传后的Actions结果为准。

## 行为回归清单

| 情境 | 期望行为 |
|---|---|
| 随手拍一张，没有参数 | 先识货、问发货与关键事实，不直接猜参数/生整套 |
| 多图混合两款 | 分SKU，不串容量、尺寸和配件 |
| 选择类目，未定图数 | 先消费者/任务/痛点，再利益证据与逐图必要性，最后建议数量 |
| 已指定八张 | 作为约束，不重复问；内容冲突时解释取舍再确认变更 |
| 三类目各八张 | 三份定位、独立标题策略，共24图位状态 |
| 续航要强卖但只有容量 | 问实际档位时长/条件，不从容量推续航；其他创意可继续 |
| 真实1/2/4件可选，各附线 | 标题开头与主图顶部都是1/2/4pc，线不计主商品 |
| 独立2件款，另链接有1/4件 | 当前两处只写2pc |
| 商家未知数量 | 先问，不默认1pc；正式主图/标题暂停 |
| 商家明确要求无字主图 | 指出与件数约定冲突，等商家裁定，不暗中省略 |
| 同款多灯场景、单件售卖 | 明确实际每包件数与演示关系，不制造套装或连线 |
| 无回看能力 | 保留视觉待验，不声称实际件数和排版通过 |
| 非灯具 | 采用其真实任务，不机械套容量/防水等灯具问题 |
| 最终交付 | 图片、数量前置标题、消费者/时机/痛点、逐图贡献与状态齐全 |

新增回归时使用商家式输入，记录原始输出；不要把期望答案提前传给被测Agent。一次合格不是跨模型稳定率。

## 本版本已观察到的结果

- 件数规则加入前，同样多规格输入得到的标题以容量开头，主图用“CHOOSE 1, 2 OR 4”表达，未满足本次准确标签前置要求。
- 规则加入后，独立文字试跑输出 `1/2/4pc` 的标题与主图顶部；另一次独立2件款试跑输出 `2pc`，未把线材算入，也未混入另链接选项。另一次照片含三盏但未确认发货数量的试跑，Agent先问实际数量及全部可选规格，没有猜作3pc。
- 之前的工作流试跑覆盖单类目、三方向、固定八张、未知续航和非灯具交付；曾发现图数提前和解析遗漏，已对应收紧字段与输出顺序。

本次没有重新批量生成商品图，没有运行公开GitHub远程CI，也没有对未观察的宿主或模型给出通过结论。

## 实图检查卡

- 对照原图核轮廓、颜色、部件、接口、标记和款式。
- 核主图顶部件数、标题首字段、实际发货与可选规格一致。
- 文字放大核拼写/数字/单位，缩小预览核可读性；字不出框、不盖关键商品。
- 人物真实参与活动，手部与物体接触合理，挂点确实可用。
- 同卖点跨图有证明增量，不只是换背景/天气。
- 单件、多件演示、配件与道具不混淆。
- 雨景、光效、比较或徽章没有引入未知性能。
- 每套数量兑现，未验/失败/未生成分别记录。
