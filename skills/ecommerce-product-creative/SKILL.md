# 商品创意工作流

项目版本：v1.0.1。

采用对话驱动：用户决定商品事实、选用类目、制作规模与是否做规格差异；Agent负责提出有依据的推荐、类目痛点、标题策略和视觉设计。保留具体卖点、使用结果、局部说明、功能分层和有层级的字体/色块。纯指令使用宿主已有工具，不新增服务。

## 第一优先：完整任务必须先对话

**识货 → 补齐关键事实 → 人选主辅类目 → 类目需求/痛点与卖点证据分析 → 定向补问 → 提议逐图作用与最小充分图数 → 人定规模及多链接类型 → 核对差异并校正策略 → 开工确认 → 设计/制作 → 验收 → 图片＋标题＋商家解析。**

[接单与对话状态](references/intake.md) 是完整制作和完整方案的前置。未知不等于已询问；推荐不等于用户选择；“直接做/帮我选/你判断”不自动补齐未决参数、类目或图数。未开工时允许展示需求判断、候选短卖点与逐图必要性简表，帮助用户决策；不先输出完整分镜、逐图提示词、最终标题或生图。

已有明确答案不重复问，用户可在一条消息回答多个关卡。已有具体版本的开工确认才可直接执行；只有一句“做一套”不能当类目、图数或差异化决策。非必需信息可在用户明确回复未知/不适用/本次不用后降级，但不能未经询问就跳过相关关键字段。

## 先选范围

| 请求 | 路径 |
|---|---|
| 只诊断旧图或只要类目建议 | 只读图/文字并给诊断或候选；不自动制作 |
| 只改一条标题/卖点 | 确认该项所需商品与任务信息，直接交该项；不强迫完整接单 |
| 完整方案、单套图文或多套多链接 | 完成对话关卡及开工确认；方案委托确认后交方案，制作委托确认后生成 |

## 件数前置硬约束

必读 [数量标签](references/quantity.md)：确认每个链接真实主商品件数后，最终标题第一个字段和实际主图顶部都必须有准确标签；单件 `1pc`，真实1/2/4件可选则 `1/2/4pc`，含最小规格且不合计配件。未知先问，不默认。它是本项目约定，不能以平台惯例/视觉偏好省略；明确禁字要求有冲突时先由用户裁定。交付必须看实际主图，文本检查通过不等于图像通过。

## 开工硬关卡

完整任务逐项留状态与用户答复来源，详细问法见 intake；类目/链接表见 [逐链接合同](references/listing-brief.md)。

1. **事实关。** 锁商品身份和发货。按品类问关键规格：电池灯具必须问电池容量和供电、防水有无/等级、尺寸；便携主张需问重量与实际携挂方式。非电池商品容量不适用；其他品类改问对应核心参数。未知需用户明示，不能用图像猜。
2. **类目关。** 展示主推荐与辅助候选、依据和状态，然后等用户选择。用户可以另选不在列表的类目；核用途与来源，不强迫首推或虚构节点。无对应树可由用户确认通用方向，仍标路径待映射。
3. **需求关。** 选择类目后、建议图数前，必须调用 [类目需求组件](references/category-demand.md)，逐类目/实际SKU给出消费者与时机、任务、痛点优先级、事实到利益的推导、证据缺口及场景候选。区分可开放创作的卖点方向/营销表达与需核实的商品能力：不让用户逐个设计或批准卖点，只补问影响承诺的性能/事实缺项；由Agent提出判断，不把卖点设计工作丢给用户。输出简洁决策依据，不输出内部逐步思维。
4. **规模关。** 依据去重后的购买疑问与证明任务提议图位；每张必填“为什么存在、比其他图新增什么、可否合并”。再由用户确定几套、对应类目/链接、每套总张数。三类目各八张为三个L-ID、24个展示图位；不因同款强制同图数。已指定图数先作为约束，不重问；内容冲突才提出具体取舍供确认。复用素材数与展示图位分开。
5. **多链接/差异关。** 已明确单套单款且无开发需求时记不适用。多链接或开发需求则问清同款多类目创意、已有真实不同款、开发差异款还是混合；SKU归属未明且影响需求判断时提前问。按 [事实](references/facts.md) 核算；未知不能编尺寸/容量，开发目标不进入销售成品。新差异影响卖点或图数时回需求关校正受影响套。
6. **开工关。** 给简洁确认单：用户所选类目、消费者/任务/痛点与证据、逐图必要性及每套数量、SKU/发货、未知与不用主张、差异结果、各条标题策略/场景、总数和交付范围。等用户确认该版本；已答信息不重问。

仅当关卡已通过，才设计完整分镜和调用生图。不会把“强制对话”做成不断重问或要求用户做设计；每轮通常至多三组有关联问题，回答后再推进。

## 制作能力与范围

盘点读图、绑定商品原图、准确叠字与回看能力。不能读图就只用已确认文字，不能生成或不能绑定原图就交文案/提示词，不能把相似商品当成品。不能回看则先交关键样图待验与剩余指令；用户明确允许未验整套才继续，全部保留待验。服从宿主实际权限与付费授权。

## 确认后的执行链路

1. 按 [事实](references/facts.md) 建R图号/SKU/事实ID，按 [交付](references/contract.md) 锁规格、语言、计数和已确认范围。
2. 沿用开工前 [需求组件](references/category-demand.md) 的判断、证据与图位贡献，不在开工后才补画像；照明查 [用户类目表](references/categories.md)，其他品类用对应来源。按 [链接规划](references/listing-plan.md) 沿用并锁定L-ID，不把创意版本误作新SKU或发布许可。
3. 按 [卖点](references/selling-points.md) 将已确认利益组合落成各链接独立标题和图内短词。类目决定关注点，不创造性能；不能按收到的参数顺序逐项制图。
4. 按 [视觉策略](references/visual-strategy.md) 比较两个可行方向并记录选定项；用户已批准风格则留沿用来源。优先 [销售构图](references/sales-composition.md) 的使用结果、局部说明、功能分层。用户负责业务选择，Agent负责视觉设计。
5. 按 [图像执行](references/images.md) 先做同类目内的活动候选，再按已确认图数编排；具体分配人物、携带、悬挂、群组布置、操作和选购角色，不能只重复桌面静物。商品身份由原图锁定，背景/合理机位可创作。通用范例见 [创意写法](references/creative-patterns.md)，不是默认SKU事实。
6. 分镜须列L-ID/版本、痛点/利益ID、买家疑问、存在理由与信息增量、实际SKU/事实ID、主题、动作/信息、机位、版式区域、准确文字和验收条件。指定拼图/卡片不能改成编号清单，不能因“平台惯例”擅改无字白底。
7. 按 [验收](references/review.md) 回看产物与整套，局部修复、保留重试上限与未知状态；按已确认L-ID和图数交付。每套同时交一条最终标题和 [商家解析](references/contract.md)：产品/类目、消费者/时机、痛点/购买理由、图数与逐图贡献、标题与视觉取舍。解释实际结果，未完成项明示，不宣称转化已验证。

## 变更与规则归属

内部记录对话状态、事实、已选类目和范围、L-ID合同、视觉卡、分镜与产物；向用户展示必要决策和结果。类目/套数/规格差异更改后更新确认单版本，重新确认受影响范围；图文按L-ID/版本及事实ID追溯。

对话关卡以 intake 为准；需求判断/图位必要性以 category-demand 为准；事实/差异核算以 facts 为准；类目/标题/场景绑定以 listing-brief 为准；刊登与方案矩阵以 listing-plan 为准；交付与语言以 contract 为准；视觉与验收按相关模块。不能用任何旧版“直接做就继续”的句子绕过本版关卡。只输出方案不能标成图片已完成。
